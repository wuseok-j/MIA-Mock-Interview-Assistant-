# 협업 가이드 — GitHub Desktop으로 작업 올리기

> 한 줄 요약: **내 브랜치에서 작업 → PR 올리기 → 단톡에 링크 → 장우석이 확인하고 합친다.**
> `main`(모두가 같이 쓰는 원본)에는 아무도 직접 올릴 수 없게 막아 두었다. 실수해도 원본이 망가지지 않으니 겁먹지 말 것.

## 왜 이렇게 하나요?

4명이 한 폴더를 동시에 고치면 서로 덮어쓰기 쉽다. 그래서
- 각자 **브랜치**(내 작업용 복사본)에서 작업하고
- 끝나면 **PR**(Pull Request = "제 작업 합쳐 주세요" 요청서)을 올리고
- 장우석이 확인한 뒤 원본(`main`)에 합친다(**머지**).

```
main ──────────●─────────────●──────>   (원본)
                \           /
 content/화재검수 ●──●──●──●            (내 브랜치: 작업 → PR → 머지)
```

3. `File → Clone repository` → `wuseok-j/MIA-Mock-Interview-Assistant-` 선택 → 저장 위치 정하고 **Clone**

## 작업할 때마다 (이 순서 그대로)

### ① 최신 원본 받기
- 상단 **Current branch** 가 `main` 인지 확인
- **Fetch origin** → (버튼이 바뀌면) **Pull origin**

### ② 내 브랜치 만들기
- **Current branch → New branch**
- 이름: `종류/내용` — 예) `docs/서비스조사`, `content/화재검수`, `feat/채팅화면`
- **Create branch** (기준이 `main` 인지 확인)

### ③ 작업하기
평소처럼 VS Code 등에서 파일을 고친다. GitHub Desktop 왼쪽에 바뀐 파일 목록이 뜬다.

### ④ 커밋 (저장 지점 만들기)
- 왼쪽 아래 **Summary** 에 무엇을 했는지 한 줄 — 예) `크랙·제타 조사표 추가`
- **Commit to 내브랜치이름** 클릭
- 작업 중간중간 여러 번 해도 된다.

### ⑤ 올리기 (push)
- 처음엔 상단 **Publish branch**, 그다음부터는 **Push origin**

### ⑥ PR 올리기
- **Create Pull Request** (또는 `Branch → Create pull request`) → 브라우저가 열림
- 제목·내용 작성 (양식이 자동으로 나옴) → **Create pull request**
- **단톡에 PR 링크 남기기** ← 이게 있어야 장우석이 바로 본다

### ⑦ 확인 기다리기
- 장우석이 **머지**하면 끝. 고칠 부분이 있으면 PR에 댓글이 달린다.
- 수정 요청을 받으면: 같은 브랜치에서 고치고 → ④ 커밋 → ⑤ Push origin. **PR은 새로 만들 필요 없다** (자동으로 추가됨).

### ⑧ 머지된 뒤
- **Current branch → main** 으로 돌아와서 **Fetch origin → Pull origin**
- 다음 작업은 다시 ② 새 브랜치부터

## 자주 겪는 문제

| 상황 | 해결 |
|---|---|
| push 했더니 거부됨 / "protected branch" 오류 | `main` 에서 작업한 것. 커밋하지 말고 장우석에게 연락 (변경 내용은 살릴 수 있음) |
| Publish 버튼이 안 눌리거나 권한 오류 | 처음 한 번만 1번(초대 수락)을 했는지 확인 |
| "conflict(충돌)" 라는 말이 나옴 | 혼자 해결하지 말고 화면 캡처해서 장우석에게 |
| 어떤 브랜치에 있는지 헷갈림 | 상단 **Current branch** 확인. 작업은 항상 내 브랜치에서 |
| `.env` 파일이 변경 목록에 보임 | **절대 커밋 금지** (API 키). 원래는 자동으로 숨겨지니 보이면 바로 알리기 |

## 규칙 3개만 기억

1. **`main` 에서 작업하지 않는다.** 시작 전 Current branch 확인.
2. **PR 올리면 단톡에 링크.**
3. **막히면 30분 안에 질문.** 캡처 한 장이면 충분하다.
